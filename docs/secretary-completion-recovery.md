# 秘書エージェントの完了判定と回復（2026-10-20）

## 調査した事象

10/19 08:00 JST の定期メール確認では、最初の担当が12件を読んだと
報告した。親は、検索範囲と30件上限の説明が不確かだと認識し、件数の
独立照合と、別担当による記憶保存を依頼した。

照合担当は22イテレーション、約373秒後に `cancelled / aborted`、本文なしで
終了した。300秒の子期限を超えているのは、キャンセル後もSDK・実行中の
ツールが停止するまで待つ仕組みがあるため。記憶担当は完了していた。
親は照合を再依頼せず、未確認である旨を添えて最終回答を作り、その後の
配信専用の再指示で送信した。したがって、単なる「未完了に気づかなかった」
事例ではなく、気づいた後の回復判断が不足した事例だった。

保存されていたモデルI/O 278ファイルの入力履歴から、重複するツール呼出しIDを
除いて47回の委譲・再開結果、54件の子結果を確認した。実行結果は completed 42、
partial 9、cancelled 3。これは保持されていた履歴の集計であり、全期間の
成功率ではない。ほかに、回数上限、APIエラー、認証期限切れ、アクセス拒否、
タイムアウトが見られた。これらを一律に再試行すべきではない。

## 考察

- SDKの終了状態は、依頼の達成を証明しない。正常終了した担当でも、件数や
  対象範囲の説明が不足していた。親が受入条件と根拠を照合する必要がある。
- 従来の再開は回数上限の履歴に限定されていた。タイムアウトには再開IDがなく、
  残作業の切り出しと引き継ぎを別途指示する必要がある。
- 親への「確認すること」という指示だけでは、注意書きを添えて終了できてしまう。
  最終回答を公開する手前で、未解決の委譲を機械的に拾う必要がある。
- 全文読解、全件列挙、支払い確認などをまとめた照合は大きくなりやすい。
  列挙・読解分類・照合を分け、IDと途中結果を再利用する。
- 書き込み済みのタスクを丸ごと再実行すると、二重登録・二重送信になり得る。
  元の目的の再生ではなく、未完了部分の回復に限定する。

## 実装

1. 子専用 `report_task_result` で、完了／部分完了／外部要因による停止、
   根拠と残作業を構造化した。報告のない正常終了は未検証として扱う。
2. 全件確認向けに `requireCoverage` とID集合の照合を追加した。列挙・読解・
   分類の集合とページ完了フラグを検査し、不一致を部分完了にする。
3. `taskRef` と `followUpTo` で未完了と後続依頼を関連づけた。
   後続は全件確認の要件を引き継ぎ、成功した兄弟タスクを再実行しない。
4. 未解決の委譲があれば、親の暫定回答を公開せず、同じ履歴に最大2回の
   完了レビューを入れる。子の合計8回という既存予算は維持する。
5. 親・子への指示を、受入条件、根拠、途中結果、範囲を絞った再依頼、
   副作用の読み戻し、認証・権限の拒否では停止する方針に揃えた。

対象はこのforkのCline委譲モード。DBスキーマ、依存パッケージ、認証設定、
過去のタスクやメールには変更を加えていない。新しい指示とツールは起動時に
組み立てるため、個別グループへのプロンプトの手書き追加は不要。

## 検証と限界

実SDKとローカルの模擬応答を使い、早すぎる注意書きの保留、親の再依頼、
残りの照合、最終回答1回のみの公開を通して検査する。ほかにタイムアウト、
回数上限からの再開、成功済み操作の非再実行、予算・期限切れ、外部ブロッカー、
未報告、ID集合の不一致、通常の継続とツールを使わない回答補正を検査する。
実アカウントへの再送や過去バッチの再実行は行わない。

2026-10-20の検証結果：エージェント全体690件成功・既存3件スキップ、
失敗0件。実運用と同じコンテナイメージでネットワークを無効化した
関連42件も成功した。ホスト側Cline検査3件、ホストのビルド、
エージェント側TypeScript型検査も成功した。

報告とID集合はモデルが提出する証拠なので、実際のAPI応答との一致や
全件取得を独立して保証するものではない。回復も上限内の親判断であり、
必ず成功する保証はない。上限・外部依存で完了できない場合は、確認済みの範囲と
具体的な未完了理由を報告する。レビュー中に明示的ツールで既に実行された
操作や送信は取り消さない。

切り戻しは今回のコード変更をrevertし、同じサービスを再起動する。
データ移行は不要。

## 10/20朝の追跡調査

08:00:42 JSTにスケジュールは起動したが、最初の委譲に
`followUpTo: 00000000-0000-0000-0000-000000000000` が入った。
先行タスクが存在しないため入力エラーになり、同じ参照エラーを50回繰り返した。
08:06:49に回数上限で失敗し、メールの取得・読解担当は一度も起動せず、
メール報告の送信もなかった。翌日08:00の予約は維持されていた。

前回追加した任意の参照項目は文字列のみで、参照なしをnullで明示できなかった。
また、エラー文が新規依頼でどう修正するかを説明せず、入力不正の反復も
止めなかった。任意項目のnullを許可し、新規依頼ではnullを使うこと、
実際に返された参照だけを使うことをスキーマ説明・親への指示・エラー文に
明記した。3回の不正入力で次の親モデル要求を停止する制限も加えた。

検証には、実SDKのResponses送信ペイロードでnullが許容されること、新規依頼の
null参照、子のnull coverage、ダミー参照の3回停止を追加した。
今朝分の再実行や報告の再送は、この調査では行っていない。
